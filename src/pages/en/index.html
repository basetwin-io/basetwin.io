The open-source digital twin core for NGSI-LD

Why BaseTwin

A context broker stores entities. A twin needs more.

NGSI-LD gives a twin its entities, relationships and history. It does not say whether a number was measured or simulated, which licence it came under, or what the city looked like before a scenario changed it. BaseTwin adds those services on top of a standard broker and keeps the broker replaceable.

Values that explain themselves

Every value carries its kind (observation, estimate, forecast or simulation), quality, uncertainty, method, resolution, validity and provenance. A missing value is never 0.

Scenarios that never touch reality

Workspaces overlay each other read-only, from public to customer to scenario. Simulations are written to their own workspace and never overwrite observed state; as-of queries return the twin as it was known at a point in time.

Governance from the first byte

A licence gate at ingest, a catalog of datasets and versions, attributions and policies, and a provenance record of every run. Data can be traced from a published value back to its source.

Two products

One codebase, one image, two products

Start with governed data sharing and add the twin when a model or an application needs it. A deployment selects its products with one setting; /v1/capabilities reports what is running.

BASETWIN_PROFILE=dataspace

Data Space

Governed data sharing from many sources.

  • Catalog of datasets and versions, published as DCAT 3
  • Licences with an ingest gate, attributions, ODRL policies
  • Provenance of every run, exported as PROV-O
  • Immutable raw data, distributions and exports with signed links
  • With a broker: the NGSI-LD context hub with value semantics, domain packs, bridges, pipelines and retention

Features

What is in the core

Twin data and semantics

  • NGSI-LD entities, relationships and temporal history on a context broker (Scorpio)
  • FIWARE Smart Data Models and domain packs
  • A schema registry: allowed kinds, minimum display resolution, official-source rule
  • Workspaces as NGSI-LD tenants with a read-only overlay hierarchy

Data space and governance

  • Datasets and versions with freshness objectives
  • Licences, attributions, ODRL policies, DCAT 3 catalog
  • Exports as CSV, GeoParquet and GeoJSON with signed links
  • Context pipelines triggered by writes; retention of history

Models and scenarios

  • Model plugins read through an as-of context
  • Outputs are tagged estimate, forecast or simulation and linked to a model run
  • Scenario workspaces compute impact against a frozen parent state

Geospatial

  • JIS X 0410 grids with resolution-aware aggregation (GeoJSON, Arrow)
  • Cloud Optimized GeoTIFF rasters with a STAC 1.0 catalog
  • OGC API Features and Tiles (vector tiles)
  • CityGML building import

Interfaces and extensibility

  • Twin API, a controlled NGSI-LD proxy, an admin console
  • Python and TypeScript SDKs
  • Plugin API for connectors, bridges, models, promoters, pipelines and domain packs
  • OIDC authentication with per-workspace grants

Operations

  • A development stack on Docker Compose, a Helm chart for Kubernetes
  • Opt-in OpenTelemetry traces and metrics
  • No owned infrastructure: BaseTwin connects to a broker, a database, an object store and an OIDC issuer by URL

Scope

Where BaseTwin sits in a digital twin

A digital twin is a digital representation of a physical entity, process or system that uses data and models to represent its state, behaviour and evolution over time. Most architectures describe five components, plus an orchestration layer when several twins work together. BaseTwin is the core of the twin: components 2 to 5.

  1. Outside the core

    Physical entity

    The real object, environment, process or system. Reached through connectors and bridges.

  2. In BaseTwin

    Data and connectivity

    Connector plugins for batch ingest, bridge plugins for continuous import, a catalog with a licence gate, promotion into workspaces, pipelines and retention.

  3. In BaseTwin

    Digital representation

    NGSI-LD entities and relationships with history; geometry, grids, rasters and buildings; mandatory value semantics; workspaces and as-of queries.

  4. In BaseTwin

    Models and simulation

    Model plugins with fit, predict and validate; outputs tagged by kind with run provenance; scenario workspaces. Simulation engines are plugins by design.

  5. In BaseTwin

    Services and applications

    Twin API, NGSI-LD, OGC API Features and Tiles, STAC, catalog, provenance and export APIs, SDKs and an admin console. End-user applications are built on these APIs.

  6. Partly

    Orchestration of several twins

    Point-to-point bridges, dataset discovery through the DCAT catalog and semantic alignment through JSON-LD contexts. Federation across brokers and a registry of twins are system-level concerns.

The link between the physical and the virtual side is one-way today: from the physical side into the twin. Commands and actuation are not part of the core.
